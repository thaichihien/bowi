# Bowi — Requirements (v0.1, CLI)

> **Bowi** is short for *bowerbird*, the bird that collects scattered things and arranges them to be seen. Bowi does that to your pull request.
>
> Audience: Claude Code (implementer) and human contributors.
> Status: draft for phase 1 implementation.
> Language: TypeScript (Node.js). Go may replace the analysis core later if performance requires it; keep module boundaries clean so that is possible.

---

## 1. Problem statement

### 1.1 Original statement (from the project owner, kept as written)

> As more and more code are generated by AI Agents or the development flow is generating code, open pr to repo,... Then let human review the pr, the diff,... But the diff can be a lot, when human open a pr, For example github, it should folder tree with files sorted alphabetical order (like same folder tree we code), then we started reading pr files from top to bottom (we see unrelated file first or have to find changes files), with a lot of diff lines,... Then I have an Idea to make this pr review better by showing group of changes, related files, summary the code changes, better showing up in UI,... This just raw idea but want to know how far can I develop this.

### 1.2 Restated

AI agents and automated flows now produce large pull requests quickly. A human still has to review them. Review tools such as GitHub show changed files as an alphabetical folder tree, so the reviewer:

- reads unrelated files first (lockfiles, config, formatting changes) and hunts for the files that matter;
- reads consumers before the things they depend on (a controller before the service and database column it uses);
- faces many diff lines with no grouping, no "why", and no reading path.

**Bowi** turns a PR (or a local branch) into a guided review: related changes grouped together, ordered so foundations come before the code that uses them, noise collapsed, and every group explained with evidence. The result is one self-contained HTML file a human opens in the browser.

## 2. What people report (background)

Research summary from public sources (links in §16). Key points:

- **Size and volume.** AI-assisted PRs are about 2.6× larger than unassisted ones and wait about 4.6× longer for a first review (LinearB 2026, via CodeRabbit's guide). Salesforce saw PRs regularly exceed 20 files and 1,000 lines, with review time on the largest PRs flattening or dropping, a sign reviewers stopped engaging.
- **Alphabetical order hurts.** In an ICSE 2026 survey of 1,355 developers, only 10.2% think alphabetical file order is optimal; 57.6% say it causes context switching and fatigue; 63.9% worry it makes them miss bugs; 66% asked for customizable ordering and dependency-aware grouping. A mining study found 44.6% of 23,241 GitHub reviews already ignore alphabetical order.
- **Real situations.** Engineers describe 4,000-line diffs across 11 files; an 847-line PR approved after a 15-minute skim that shipped a 4-million-row scan; colleagues pushing huge multi-file commits with one-line descriptions; reviewers dreading code nobody understands.
- **Open source strain.** Godot, Ghostty, tldraw, curl, LLVM, llama.cpp and others added AI contribution policies or closed outside PRs. LF Research (Oct 2026) estimates about 25% of incoming PRs are low-quality AI submissions; 64% of large-project maintainers say reviews take longer.
- **Plausible but wrong.** AI code follows conventions and looks clean, which hides wrong assumptions, invented APIs, and tests that only make checks pass.
- **Missing intent.** Diffs arrive without the "why". Reviewers reconstruct intent from scattered files. Several writers call the result comprehension debt or cognitive debt.
- **Distrust of AI explanations.** Reviewers report that AI-written summaries can hide problems and are claims until code and behavior support them.

What people suggest that this project addresses:

- dependency-aware reading order (schemas, types, migrations before logic);
- separating mechanical changes (renames, moves, formatting, generated files) from behavior changes;
- grouping related changes, with a way to see why they are related;
- reviewing intent first, then code.

## 3. Goals

**Primary goal: make PR review easier to read and faster to understand for a human.**

| ID | Goal | Measured by |
|---|---|---|
| G1 | Reviewer reads related changes together | Every hunk belongs to exactly one group; groups follow the change graph |
| G2 | Reviewer reads foundations before consumers | Steps within a group follow layer order (schema → data → service → API → UI → test → docs) |
| G3 | Reviewer spends no attention on noise | Generated files, formatting-only changes and pure moves are collapsed with a summary |
| G4 | Reviewer sees hidden changes | Edits inside moved code are highlighted; nothing is ever hidden without being listed |
| G5 | Reviewer understands why things are grouped | Every group shows human-readable reasons (evidence from the graph) |
| G6 | Reviewer sees relevant code outside the PR | Unchanged callers of changed symbols are listed |
| G7 | Works without AI | Full report produced with AI disabled; AI only improves names and summaries |
| G8 | Private by default | No code leaves the machine unless the user explicitly enables AI |

## 4. Non-goals (out of scope for v0.1)

These belong to other components or later phases. Do not implement them.

- **Automated test pipelines** — running tests, generating tests, coverage collection.
- **CI checks and gates** — pass/fail status checks, PR size limits, blocking merges, lint enforcement.
- **Automated code review comments** — the tool does not judge code quality or post review comments.
- **Auto-fixing or rewriting code**, splitting a PR into new branches, or creating stacked PRs.
- **Posting to GitHub on its own** (bot comments, check runs). Planned for phase 2 via a renderer that reads `review-plan.json`. The reviewer's own comments, sent when the reviewer asks, are in scope since M11 (§15 #70).
- **Web service, accounts, database, team dashboards.** Planned for phase 3.
- **MCP server.** Planned for phase 2.
- **Running the target repository's code** — never install its dependencies, run its scripts, build it, or start language servers in v0.1.

Allowed but strictly as **reading aids**: short, non-blocking hints such as "database migration" or "new public endpoint" (§7.10). Hints never produce pass/fail results or exit codes.

## 5. Users and use cases

| ID | User | Use case |
|---|---|---|
| U1 | Reviewer | `bowi <github-pr-url>` → opens a grouped, ordered review of someone else's PR |
| U2 | Author (often with an AI agent) | `bowi --local` → reviews their own branch or agent output before opening a PR, to check it reads well and contains nothing unexpected |
| U3 | Script or later tool | `bowi <url> --json-only` → produces `review-plan.json` for other renderers |

## 6. Glossary

| Term | Meaning |
|---|---|
| Base | The branch the PR merges into (e.g. `main`) |
| Head | The PR branch / the new code |
| Merge base | Commit where head split from base. Diffs are computed `mergeBase..head` so unrelated changes on base are excluded |
| Snapshot | Base SHA, head SHA, merge-base SHA, plus a way to read any file at either version |
| Hunk | One continuous block of changed lines in one file, with surrounding context |
| AST | Syntax tree produced by a parser (tree-sitter); ignores whitespace and formatting |
| Symbol | A named code unit: function, method, class, interface, type, exported variable, or a Markdown section |
| Change graph | Nodes = changed symbols (or hunks with no symbol); edges = relationships with a weight and evidence |
| Group | A set of related hunks presented together, e.g. "Email verification" |
| Step | A sub-part of a group at one layer, e.g. "Data shape", "Service", "Tests" |
| Layer | Architectural role used for ordering: `schema`, `data`, `domain`, `service`, `api`, `ui`, `config`, `test`, `docs`, `unknown` |
| Noise | Hunks a human rarely needs to read line by line: generated, formatting-only, pure move |
| Review plan | `review-plan.json`, the engine's output contract |

## 7. Functional requirements

Priorities: **P0** = required for v0.1, **P1** = should have in v0.1, **P2** = later / optional.

### 7.1 CLI

| ID | Pri | Requirement |
|---|---|---|
| CLI-1 | P0 | `bowi <github-pr-url>` analyzes a GitHub PR (`https://github.com/<owner>/<repo>/pull/<n>`) |
| CLI-2 | P0 | `bowi --local [--base <branch>]` analyzes the current repository: merge-base of `--base` (default: `origin/HEAD`, else `main`, else `master`) vs the working tree, including staged, unstaged and untracked (not ignored) files |
| CLI-3 | P0 | Writes `review-plan.json` and `review.html` to `--out <dir>` (default `./.bowi/<repo>-<pr-or-branch>/`) |
| CLI-4 | P0 | `--json-only` writes only `review-plan.json` |
| CLI-5 | P1 | Opens `review.html` in the default browser unless `--no-open`; never opens when stdout is not a TTY |
| CLI-6 | P0 | Shows a step-by-step progress display with timing per stage (see §11.2); `--verbose` adds details, `--quiet` suppresses all but errors |
| CLI-7 | P1 | `--order dependency|tests-first` sets the default reading order in the report |
| CLI-8 | P2 | `--ai` enables AI enrichment (off by default; see §7.11) |
| CLI-9 | P1 | `--config <path>` loads a config file; default is `.bowi.json` in the repo root if present |
| CLI-10 | P1 | `bowi cache clear` and `--cache-dir <dir>` (default OS cache dir, e.g. `~/.cache/bowi`) |
| CLI-11 | P0 | Exit codes: `0` success, `1` usage error, `2` source error (auth, not found, network), `3` analysis error. Hints never affect exit codes |
| CLI-12 | P0 | Clear error messages with a next step (e.g. "Set GITHUB_TOKEN or run `gh auth login`") |
| CLI-13 | P0 | `bowi serve <dir> [--no-open]` serves a report folder on `127.0.0.1` (free port, random token in the address, `Host` and `Origin` checked) so its page can save comments into `review-plan.json` and `review.html`; Ctrl+C stops it. `--serve` on a run writes the report, then serves it (not with `--json-only`). A folder without a report, without `review.html`, or with a report from before comments exits 1 with what to run. Since M10 (§15 #65) |
| CLI-14 | P1 | `bowi comments <dir>` lists the comments of a report; `--markdown` prints them as Markdown, the same text as "Copy all as Markdown". Since M10 |
| CLI-15 | P1 | A run writing into a folder whose plan has comments carries them over (§15 #64) and prints how many were kept, moved and outdated; `--no-comments` leaves them out of `review.html` (the plan keeps them). Since M10 |
| CLI-16 | P0 | `bowi comments push <dir>` sends a report's comments to its pull request, listing what goes where and as whom and asking first (`[y/N]`). `--yes` skips the question and stops with an error if the pull request has new commits since the report; `--now` posts at once instead of as a pending review; `--outdated` includes outdated comments. Without a terminal and without `--yes` it refuses. A second push sends only what is new. Since M11 (§15 #70) |

### 7.2 Sources

| ID | Pri | Requirement |
|---|---|---|
| SRC-1 | P0 | Both sources produce the same `Snapshot` interface; the engine must not know which source was used |
| SRC-2 | P0 | GitHub source reads PR metadata (title, description, base/head refs and SHAs, author, linked issues if present in description) with a token from `GITHUB_TOKEN`, else `gh auth token` if `gh` is installed |
| SRC-3 | P0 | GitHub source gets the merge-base SHA from the compare API, then fetches only the needed commits |
| SRC-4 | P0 | Code is retrieved with the `git` binary using a cached partial clone (`--filter=blob:none`), reused across runs |
| SRC-5 | P0 | Do not use the PR files API for diff content (it truncates large files); compute the diff locally |
| SRC-6 | P1 | Collect commit messages between merge base and head (used for naming and grouping signals) |
| SRC-7 | P0 | Never run code from the target repo (no installs, scripts, builds, hooks). Run git with hooks disabled |

### 7.3 Diff and hunks

| ID | Pri | Requirement |
|---|---|---|
| DIFF-1 | P0 | Compute `git diff -M --find-renames mergeBase head` (or working tree for local) with 3 lines of context |
| DIFF-2 | P0 | Parse into `FileChange[]` and `Hunk[]` with stable IDs (`<fileIndex>:<hunkIndex>` or hash-based; must be stable across runs on the same input) |
| DIFF-3 | P0 | Handle added, deleted, renamed, copied, mode-only and binary files. Binary files get a file entry with no hunks |
| DIFF-4 | P1 | Very large files (configurable, default > 5,000 changed lines in one file) are summarized, not embedded in full |

### 7.4 Parsing

| ID | Pri | Requirement |
|---|---|---|
| PARSE-1 | P0 | Parse old and new versions of each changed text file with `web-tree-sitter`, grammar chosen by extension |
| PARSE-2 | P0 | Supported in v0.1: TypeScript, TSX, JavaScript, JSX, JSON. **P1**: SQL, YAML, Markdown (sections as symbols). **P2**: Go, Java, Python. YAML and Markdown done in M6; SQL deferred (§15 #41). Vue, Svelte and Astro single-file components since M14: their scripts as TypeScript, the markup as text with the names it uses (§15 #74) |
| PARSE-3 | P0 | Files with no grammar fall back to tier 0 (text-only analysis); they are never dropped |
| PARSE-4 | P0 | A parse error in one file must not fail the run; mark the file `parseStatus: 'error'` and use tier 0 for it |
| PARSE-5 | P1 | Cache parse results by content hash |

### 7.5 Noise classification

| ID | Pri | Requirement |
|---|---|---|
| NOISE-1 | P0 | **Generated:** built-in patterns (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`, `*.snap`, `*.min.js`, `dist/**`, `*.gen.ts`, `*.generated.*`), files with `@generated` / `DO NOT EDIT` headers, and `linguist-generated` in `.gitattributes`; extendable via config |
| NOISE-2 | P0 | **Formatting-only:** old and new ASTs are equal after ignoring whitespace and comments → hunk kind `format` |
| NOISE-3 | P0 | **Moves:** fingerprint removed and added symbols (normalized AST hash); exact match across or within files → `move` |
| NOISE-4 | P0 | **Moved with edits:** similarity ≥ 0.8 (configurable) → `move` with `changedLines` listing the lines that differ; those lines must be highlighted in the report and are **never** treated as noise |
| NOISE-5 | P1 | Text-level move detection for files without a grammar (normalized line-block hashing, min 5 lines) |
| NOISE-6 | P1 | Lockfile summary: list added/removed direct dependencies by reading `package.json` diff alongside the lockfile |
| NOISE-7 | P0 | Noise is collapsed, never removed: every noise hunk remains in the plan and viewable as raw diff |

### 7.6 Symbol mapping

| ID | Pri | Requirement |
|---|---|---|
| SYM-1 | P0 | Map each hunk to its innermost enclosing symbol(s) in old and new ASTs, using tree-sitter `tags.scm`-style queries per language |
| SYM-2 | P0 | Classify each changed symbol: `added`, `deleted`, `signature`, `body`, `renamed`, `moved` |
| SYM-3 | P0 | Hunks outside any symbol (top-level imports, config) map to a file-level pseudo-symbol |
| SYM-4 | P0 | Assign a layer to each file/symbol: framework plugin first, else path heuristics (`migrations/` → schema, `entities/` `models/` → data, `helpers/` `utils/` `lib/` `common/` `shared/` and `*.helper.*` `*.utils.*` → util (since M5.5, §15 #33), `services/` → service, `controllers/` `routes/` `handlers/` `resolvers/` → api, `components/` `pages/` → ui, `*.spec.*` `*.test.*` `test/` → test, `*.md` `docs/` → docs, config files → config) |

### 7.7 Change graph

Edges carry `type`, `weight` (0–1) and `evidence` (a human-readable sentence plus file/line locations). Every edge must be explainable in one sentence shown to the user.

| ID | Pri | Edge type | Detection | Default weight |
|---|---|---|---|---|
| GRAPH-1 | P0 | `calls` | Call expression in one changed symbol names another changed symbol, with import path match where resolvable | 1.0 |
| GRAPH-2 | P0 | `uses-type` | Changed symbol references a changed type, class, interface or field | 0.9 |
| GRAPH-3 | P0 | `tests` | Test file imports or names a changed symbol/file (`x.spec.ts` ↔ `x.ts`) | 0.8 |
| GRAPH-4 | P0 | `same-symbol` | Multiple hunks in the same symbol | 1.0 |
| GRAPH-5 | P0 | `shared-literal` | Distinctive string literal or identifier appearing in hunks of different files (route paths, queue/event names, table/column names, config keys). Ignore common strings via a stoplist and minimum length | 0.6 |
| GRAPH-6 | P1 | `same-commit` | Hunks introduced by the same commit (when the PR has more than one commit) | 0.4 |
| GRAPH-7 | P1 | `co-change` | Files frequently changed together in the last N commits (default 300) of base history | 0.3 |
| GRAPH-8 | P1 | `docs-mentions` | A docs hunk mentions a changed symbol name or a new route string | 0.6 |
| GRAPH-9 | P1 | `framework` | Edges added by framework plugins (NestJS: constructor injection, controller → service, `@Processor('x')` ↔ `queue.add('x')`, `@Entity`/`@Column` ↔ migration column names) | 0.8 |
| GRAPH-10 | P0 | — | **Hub down-weighting:** an edge through a symbol connected to many changed symbols is reduced (e.g. weight × 1/log2(2 + degree)) so a shared logger or base type does not merge everything |
| GRAPH-11 | P1 | — | **Outside references:** find unchanged call sites of changed symbols with ~~`ripgrep` (or~~ `git grep` (§15 #34), limited to the top N (default 5) per symbol; stored as `outsideRefs`, not as graph nodes |

### 7.8 Grouping and ordering

| ID | Pri | Requirement |
|---|---|---|
| GRP-1 | P0 | Noise hunks (generated, format, pure move) form their own groups and are ordered last. Moves with edits form a "Moved code" group ordered before noise |
| GRP-2 | P0 | Logic hunks are clustered: connected components over edges with weight ≥ threshold (default 0.5); if a component exceeds the size cap (default 40% of logic hunks or 25 symbols), split it with Louvain community detection (`graphology-communities-louvain`) |
| GRP-3 | P0 | Singleton fallback: hunks with no qualifying edges are attached to a group via weaker signals in this order — shared literal, same commit, same directory, co-change; leftovers go into one "Other changes" group sorted by path. Never output more than one group of a single hunk unless that hunk is its own file with no relations and fewer than 3 such exist |
| GRP-4 | P0 | **Partition invariant:** every hunk is in exactly one group. Validate in code; a violation is a bug and fails the run with exit code 3 |
| GRP-5 | P0 | Each group gets `reasons[]`: the strongest edges summarized as sentences, e.g. "`AuthService.register()` calls `MailService.sendVerificationEmail()`" |
| GRP-6 | P0 | Each group gets `confidence`: `high` / `medium` / `low` from the count and weight of its internal edges; `low` groups are labeled "loosely grouped" in the UI |
| GRP-7 | P0 | Steps within a group: one step per layer present, ~~ordered by layer, then by dependency~~ ordered by dependency between steps with the layer order as the tie-break (since M5.5, §15 #33); files within a step by dependency (topological sort of edges), ties broken by path. Cycles are condensed (Tarjan SCC) and shown as one step |
| GRP-8 | P0 | Group order: by dependency between groups, ~~then by size of logic change (largest first)~~ then foundations first (the earliest layer of a group's code) and then by size of logic change (largest first) (since M14, §15 #77), moves, then noise |
| GRP-9 | P1 | `tests-first` order: within each group, the test step comes first |
| GRP-10 | P0 | Rule-based group titles (no AI): based on the most connected new or changed public symbol and the layers, e.g. "New `AuthService.verifyEmail()` and 6 related changes"; use the PR title for the largest group when there is only one logic group; use commit subject when a group maps to a single commit |
| GRP-11 | P0 | Rule-based group kind: `feature` (mostly additions, new symbols), `refactor` (renames, signature changes, moves), `fix` (small edits inside existing symbols), `test`, `config`, `docs`, `noise`, `mixed` |
| GRP-12 | P0 | Determinism: same input → identical `review-plan.json` (except `generatedAt`) when AI is off |

## 8. Output contract: `review-plan.json`

The engine writes this; renderers only read it. Types live in `packages/core/src/types.ts` and are exported. Add a JSON Schema generated from the types (P1).

```ts
export interface ReviewPlan {
  schemaVersion: 1;
  generatedAt: string;                       // ISO timestamp (excluded from determinism checks)
  tool: { name: 'bowi'; version: string };
  source: {
    kind: 'github' | 'local';
    repo: string;                            // "owner/name" or local folder name
    prNumber?: number;
    title?: string;
    description?: string;                    // markdown, as written on the host
    descriptionHtml?: string;                // only in the plan embedded in review.html: rendered + sanitized
    author?: string;
    createdAt?: string;                      // ISO timestamp the PR was opened
    baseRef: string; headRef: string;
    baseSha: string; headSha: string; mergeBaseSha: string;
    commits: Commit[];                       // oldest first
    totalCommits?: number;                   // when the host listed fewer commits than the PR has
    uncommitted?: boolean;                   // local: the working tree has changes not in HEAD
    linkedIssues?: string[];                 // "#12", "owner/repo#5" from closing keywords in the description
  };
  stats: {
    files: number; hunks: number;
    additions: number; deletions: number;
    reviewLines: number;                     // changed lines in logic hunks + changed lines inside moves
    noiseLines: number;
  };
  files: FileChange[];
  hunks: Hunk[];
  symbols: ChangedSymbol[];
  edges: ChangeEdge[];
  groups: Group[];                           // already in reading order
  overview?: string;                         // AI only (AI-3): a short overview of the whole pull request
  outsideRefs: OutsideReference[];
  hints: ReviewHint[];
  review?: Review;                           // M10: the reviewer's comments; user data, never read by the engine or compared (GRP-12)
  meta: {
    ai: { enabled: boolean; provider?: string; model?: string; effort?: string };   // model: the one that answered; effort: as configured
    languages: string[]; plugins: string[];
    order?: 'dependency' | 'tests-first';    // reading order the report opens with (CLI-7, config `order`)
    warnings: string[];                      // e.g. "src/legacy.js failed to parse; used text-only analysis"
    timingsMs: Record<string, number>;
  };
}

export interface Commit {
  sha: string;
  subject: string;
  body?: string;                             // message after the subject, trimmed
  author: CommitPerson;
  authoredAt: string;                        // ISO timestamp with offset
  committer?: CommitPerson;                  // only when it differs from the author
  committedAt: string;
}

export interface CommitPerson { name: string; login?: string }   // no email: review.html may be shared

export interface FileChange {
  id: string;
  path: string; oldPath?: string;
  status: 'added' | 'deleted' | 'modified' | 'renamed' | 'copied' | 'binary' | 'mode';
  language?: string;
  parseStatus: 'ok' | 'error' | 'unsupported';
  layer: Layer;
  additions: number; deletions: number;
  generated: boolean;
}

export type Layer = 'schema' | 'data' | 'util' | 'domain' | 'service' | 'api' | 'ui' | 'config' | 'test' | 'docs' | 'unknown';

export interface Hunk {
  id: string;
  fileId: string;
  header: string;                            // e.g. "register()" or the git @@ section text
  oldStart: number; oldLines: number;
  newStart: number; newLines: number;
  lines: DiffLine[];
  kind: 'logic' | 'generated' | 'format' | 'move';
  symbolIds: string[];
  move?: { fromFileId: string; fromStart: number; similarity: number; changedLineIndexes: number[];
          pairHunkId: string };              // both halves of a move are hunks; each points at the other
}

export interface DiffLine {
  kind: 'context' | 'add' | 'del';
  text: string;
  oldNo?: number; newNo?: number;
  html?: string;                             // pre-highlighted by shiki at build time
  noEol?: boolean;                           // line has no trailing newline ("\ No newline at end of file")
}

export interface ChangedSymbol {
  id: string;
  name: string;                              // "verifyEmail"
  qualifiedName: string;                     // "AuthService.verifyEmail"
  kind: 'function' | 'method' | 'class' | 'interface' | 'type' | 'variable' | 'section' | 'file';
  fileId: string;
  change: 'added' | 'deleted' | 'signature' | 'body' | 'renamed' | 'moved';
  layer: Layer;
  hunkIds: string[];
  oldSignature?: string; newSignature?: string;
}

export interface ChangeEdge {
  from: string; to: string;                  // symbol ids
  type: 'calls' | 'uses-type' | 'tests' | 'same-symbol' | 'shared-literal'
      | 'same-commit' | 'co-change' | 'docs-mentions' | 'framework';
  weight: number;                            // after hub down-weighting
  evidence: { text: string; locations: { fileId: string; line: number }[] };
}

export interface Group {
  id: string;
  title: string;
  titleSource: 'rule' | 'ai';
  kind: 'feature' | 'refactor' | 'move' | 'fix' | 'test' | 'config' | 'docs' | 'noise' | 'mixed';
  intent?: string;                           // AI only
  confidence: 'high' | 'medium' | 'low';
  reasons: string[];
  steps: Step[];                             // in reading order (default order)
  testsFirstStepOrder: string[];             // step ids for the tests-first mode
  summary?: string;                          // for noise groups
  dependsOn: string[];                       // group ids
  moveSuggestions?: MoveSuggestion[];        // AI only (AI-3): shown in the report, never applied
}

export interface MoveSuggestion { hunkId: string; toGroupId: string; reason: string }   // a hunk of this group that belongs elsewhere

export interface Step {
  id: string;
  title: string;                             // "Data shape", "Auth service"
  layer: Layer;
  hunkIds: string[];                         // in reading order
}

export interface OutsideReference {
  symbolId: string;
  fileId?: string; path: string; line: number;
  excerpt: string;
}

export interface ReviewHint {
  id: string;
  ruleId: string;                            // "migration", "public-route", ...
  severity: 'info' | 'attention';
  message: string;
  target: { groupId?: string; stepId?: string; hunkId?: string; symbolId?: string };
}

// M10 (§15 #64): comments written in the report. No author: the report may be shared.
export interface Review {
  body: string;                              // review summary, Markdown; '' when none
  bodySync?: ReviewSync;                     // the summary went to the host: read-only from then on
  comments: ReviewComment[];
}

// M11 (§15 #70): a record of what Bowi sent, written once. Bowi reads nothing back.
export interface ReviewSync {
  host: 'github';
  id: string;                                // the host's id of the comment (of the review, for the summary)
  url: string;                               // https
  syncedAt: string;                          // ISO timestamp
  pending: boolean;                          // sent as a pending review, rather than posted
}

export interface ReviewComment {
  id: string;                                // random, unique in the plan
  body: string;                              // Markdown, as written
  anchor: CommentAnchor;
  snippet: SnippetLine[];                    // the commented lines when written; none for a file comment
  createdAt: string; updatedAt: string;      // ISO timestamps
  status: 'active' | 'outdated';             // outdated: the lines changed since; anchor and snippet as written
  sync?: ReviewSync;                         // it went to the host: read-only from then on
}

// Like GitHub's review comments: line/side = last line, startLine/startSide = first line of a range.
export interface CommentAnchor {
  path: string;
  headSha: string;                           // head of the report the anchor belongs to
  hunkId?: string;                           // absent for a file comment
  line?: number; side?: 'old' | 'new';       // context lines are 'new' unless picked in split's old column
  startLine?: number; startSide?: 'old' | 'new';
}

export interface SnippetLine { kind: 'context' | 'add' | 'del'; text: string; oldNo?: number; newNo?: number }
```

## 11. Architecture

### 11.1 Pipeline

```
CLI
 ├─ GitHub source ─┐
 └─ Local source ──┴─► Snapshot
                          │
   ┌──────────────────────▼──────────────────────┐
   │ Analysis engine (pure stages)               │
   │  1 resolve → 2 diff/hunks → 3 parse →       │
   │  4 noise → 5 symbols → 6 graph →            │
   │  7 group/order → 8 enrich (hints, AI opt.)  │
   └──────────────────────┬──────────────────────┘
        plugins ─►        │        ◄─ cache
                          ▼
                  review-plan.json
                          │
                  HTML renderer ─► review.html
```

Each stage is a function `(input, ctx) => Promise<output>` with typed input/output, independently unit-testable and cacheable by input hash.

### 11.2 Progress output (example)

```
✓ Resolved  head 9f3c2e1 · merge base 7d8e9f0           1.2s
✓ Diff      11 files, 31 hunks                          0.1s
✓ Parsed    18 file versions (typescript, sql)          0.3s
✓ Noise     1 generated · 1 formatting-only · 1 move    0.0s
✓ Symbols   14 changed                                  0.0s
✓ Graph     14 nodes · 19 edges · 2 callers outside PR  0.4s
✓ Groups    3 (confidence: high, high, n/a)             0.0s
→ Wrote .bowi/web-app-be-482/review.html
```

### 11.3 Repository layout

Bun workspaces monorepo (Bun is the package manager and script runner for development; the published CLI targets Node ≥ 22.12 per NFR-6 and must not use `Bun.*` APIs). Internal packages use the `@bowi/` scope (`@bowi/core`, `@bowi/sources`, …); they are not published: the only published package is `@bowi/cli`, which bundles them and installs the `bowi` binary (§15 #60).

```
packages/
  cli/           entry, flags, progress (commander, listr2 or ora)
  core/          types.ts, stage functions, invariants, determinism helpers
  sources/       github.ts (Octokit + git), local.ts (git) → Snapshot
  lang/          web-tree-sitter loader, grammars (.wasm), per-language query files
  plugins/       nestjs/ (P1), plugin interface
  rules/         review hints (P1)
  ai/            provider interface, prompts, zod schemas (P2)
  render-html/   Preact UI (from the prototype) built with Vite + vite-plugin-singlefile into a template
  cache/         repo cache, parse cache, AI cache
fixtures/        scripts that build small git repos with known PRs (see §12)
bench/           grouping quality benchmark (P1, see §12.3)
```

## 12. Testing and evaluation

### 12.1 Fixtures

Create `fixtures/` scripts that build deterministic git repositories (fixed author, dates, commit order) and a "PR" as `base` and `head` branches. Required fixtures:

1. **email-verification** (the prototype example): NestJS-style TypeScript project. Head adds `emailVerified` + `verifyToken` to `User` entity, a migration, `MailService.sendVerificationEmail`, `AuthService.register` change and new `verifyEmail`, `AuthController` `GET verify-email`, a spec file, a README section; also a regenerated `package-lock.json`, a Prettier-only change to `src/utils/date.ts`, and `slugify()` moved from `helpers.ts` to `string.ts` with one changed regex line.
2. **hub-change**: a shared logger signature change touching 20 files plus one unrelated feature → must not become one group (tests GRAPH-10, GRP-2).
3. **no-links**: 8 unrelated small edits in different folders → one "Other changes" group or folder groups, no singleton explosion (tests GRP-3).
4. **rename-refactor**: a class renamed across 10 files → one `refactor` group.
5. **unsupported-language**: changes in a language with no grammar (e.g. `.rb`) → tier 0 handling, no crash.

### 12.2 Acceptance tests for the email-verification fixture

- 11 files detected; lockfile marked generated; `date.ts` hunks marked `format`; `slugify` hunk marked `move` with exactly one changed line.
- Exactly 3 groups in this order: feature group, moved-code group, noise group.
- Feature group steps in layer order: data (entity + migration) → service (mail, auth) → api (controller) → test → docs.
- Feature group reasons include "`AuthService.register()` calls `MailService.sendVerificationEmail()`" and the shared column `email_verified` between entity and migration.
- `README.md` hunk is in the feature group (docs-mentions edge via `verify-email`).
- Outside references include `AuthService.login()` if the fixture defines it as unchanged code using `User`.
- Partition invariant holds; output is byte-identical across two runs (excluding `generatedAt`).
- `review.html` opens with no network requests (assert no `http` URLs in the file other than links in content).

### 12.3 Grouping quality benchmark (P1)

Measure grouping instead of guessing:

1. Take sequences of 3–6 clean, single-purpose commits from public repos (TypeScript first).
2. Squash each sequence into one synthetic PR.
3. Score how well groups recover the original commits (Adjusted Rand Index over hunks).
4. Compare against two baselines: alphabetical (one group) and group-by-top-folder.
5. Report per language. A language is "supported" only if it clearly beats group-by-folder.

Built in M7 (`bench/`, `bun run bench`; design in §15 #45). First report (2026-10-31, 37 cases from four open-source TypeScript repositories, two of them NestJS applications): TypeScript mean ARI Bowi 0.51, folder 0.38, top folder 0.10, one group 0.00; supported (+0.14 over folder, at least as good in 28 of 37 cases). After studying the weakest cases (§15 #48): Bowi 0.52 (the weakest repository 0.41 → 0.44; 5 cases better, none worse).

1. 2. ~~License (MIT vs Apache-2.0).~~ **Decided 2026-10-28:** MIT.
3. ~~Windows support in v0.1 or v0.2?~~ **Decided 2026-10-28:** v0.2. **Changed 2026-11-02:** 0.1.1 (§15 #63).
4. ~~Should `--local` default to including untracked files, or require `--include-untracked`?~~ **Decided 2026-10-28:** included by default; `--no-untracked` opts out.
5. ~~Is `localStorage` acceptable for reviewed state when opening from `file://` in all target browsers, or should the CLI offer a tiny local server mode later?~~ **Decided 2026-10-31:** `localStorage`, kept for about one week (§15 #32).
6. ~~Default AI provider and model when `--ai` is used without config.~~ **Decided 2026-10-28:** first provider is `claude-code` (spawns the local `claude` CLI headless, uses the user's Claude Code login). Anthropic / OpenAI / Ollama API providers come later behind the same interface (AI-2). Model defaults to whatever Claude Code uses unless configured.
7. **Determinism excludes timings (M0, assumed).** GRP-12 says output is identical except `generatedAt`, but `meta.timingsMs` can never be identical across runs. Determinism checks ignore both (`comparablePlanJson` in `@bowi/core`).
8. **email-verification fixture vs NOISE-6 (M0, open).** §12.2 requires exactly 11 changed files, so the fixture does not change `package.json` even though the lockfile adds `nodemailer`. The lockfile summary must therefore read direct dependencies from the lockfile's root entry (`packages[""]` in lockfile v3), not only from a `package.json` diff. Alternative: add the `package.json` change and make it 12 files.
9. **Formatting-only includes semicolons (M0, assumed).** The fixture's Prettier change to `src/utils/date.ts` adds semicolons and line breaks, as in the prototype. NOISE-2's "ASTs equal ignoring whitespace and comments" must also ignore optional semicolons (and trailing commas), or the fixture would not count as formatting-only.
10. ~~**Comment-only edits count as formatting.**~~ **Changed in M5 (overrides NOISE-2's wording; veto if you disagree):** comment *text* counts, only comment layout (line prefixes, whitespace) is ignored. Evidence: on a real PR (sindresorhus/ky#874), 4 of 5 "formatting-only" files were edits to public API doc comments (e.g. how `HTTPError.data` behaves on timeouts) and would have been collapsed as noise.
11. **TypeScript grammar gap (M2, known limitation).** `tree-sitter-typescript` 0.23.2 (latest on npm) does not parse `export type * from '…'` (TS 5.0). Files using it fall back to text-only analysis with a warning. Fix later by building the grammar from upstream master, or by tolerating errors outside the changed lines. **Worked around 2026-11-16 (M14, owner's feedback on a pull request whose `index.ts` became text):** the word `type` in `export type *` is blanked before parsing, keeping lines and columns, so such files are parsed in full; a change between `export type *` and `export *` alone then reads as formatting.

SYM-4 puts `migrations/` in `schema`, while §12.2 expects the feature group's first step to be "data (entity + migration)". GRP-7 creates one step per layer, so M3 must either merge `schema` and `data` into one "Data shape" step or the acceptance test should expect schema → data. Proposal: one step for adjacent `schema` + `data`.
13. **Move granularity (M2, assumed).** A hunk becomes `move` only if all its changed non-blank lines belong to matched moved symbols, and the same holds for its partner hunk; otherwise both halves stay `logic`. A hunk holding several moved symbols describes the first move in `move` and lists changed lines of all. Blank lines never map to symbols.

15. **Size cap for Louvain split (M3, interpretation).** GRP-2's cap "40% of logic hunks or 25 symbols" is applied as: split only when a component has more than 25 symbols *and* more than 40% of the logic hunks. 16. **Hub down-weighting formula (M3, deviation).** GRAPH-10's example `1/log2(2 + degree)` already halves edges at degree 2 and would drop every `shared-literal` edge (0.6 → 0.38) below the 0.5 threshold. Implemented: degree counts structural neighbours (calls, uses-type, tests); factor is 1 up to 6 neighbours, then `1/log2(degree/6 + 1)`, applied with the larger degree of the two ends. Combined with a second clustering pass over the leftover symbols, a hub refactor still forms its own group (fixture hub-change).

Implemented now: strongest remaining (down-weighted) edge, same file, same directory; `same-commit` and `co-change` edges ~~arrive in M6 and then~~ take part through the edge step since M6 (weights 0.4 and 0.3, below the 0.5 threshold, so they only link changes that have no stronger link). Same file was added because import-line changes (file pseudo-symbol) belong with the rest of their file.

33. **Reading order across layers (M5.5 follow-up, owner's decision 2026-10-31).** In a NestJS pull request the services calling a new helper were read before it: steps were ordered by layer only, and the helper (in a `helpers/` folder) had no layer ("Other code", read late). 34. **`git grep` instead of ripgrep (M6, GRAPH-11).** `@vscode/ripgrep` downloads its binary in an install script (network and code at install time, which Bowi avoids), and git is already required. 35. **What history and search cost for a pull request (M6, refines §15 #24).** The cache stays blobless and shallow; each feature fetches only when it runs and keeps the result: `same-commit` deepens the head by the PR's commit count; `co-change` deepens the merge base to 300 commits (commits and trees, no file contents); outside references download the head's `.ts`/`.tsx`/`.js`/… files (never `node_modules/`) in one batch, after `rev-list --missing=print` lists what is missing (git's own lazy fetching would make one round trip per file). Measured cold: sindresorhus/ky#874 +2.4 s; nestjs/nest#18339 +6.3 s (2,193 source files; the whole cache is 3.2 MB). Warm: +0.1–0.4 s. A repository with more than 10,000 source files gets no outside references (a warning says so); `outsideRefs.maxPerSymbol: 0` turns the search off.
36. **Config of a pull request comes from its base (M6, CLI-9).** `.bowi.json` is read from the merge base, not the PR head: otherwise a PR could add `"generated": ["src/**"]` and present its own code as collapsed noise. `--local` reads the working tree (the reviewer's own checkout). `base` in the file applies to `--local` only.
37. **What counts as an outside reference (M6, GRAPH-11).** Searched: changed functions, methods, classes, interfaces, types and top-level constants (body, signature, rename, deletion; for renames and deletions the old name), not tests, docs or config. A match counts when it is not on a line the PR adds, not inside a changed symbol (that code is in the review), not in an import, comment or string, not in a generated file, and: a method `C.m` is called as `.m(` in a file that names `C`; anything else is used in its own file or in a file that imports it. Unchanged code in changed files counts (e.g. `AuthService.login()` using `User`, §12.2). Up to N per symbol, one per file first, other files before the symbol's own file. The panel heading says "Unchanged code that uses these changes" (it was "Related code not in this PR", which is wrong for unchanged lines of changed files).
38. **History edges (M6, GRAPH-6, GRAPH-7).** `same-commit`: blame assigns each added line to a PR commit (local: the working tree file against `merge-base..HEAD`, uncommitted lines have none); symbols in different files whose added lines share a commit are linked as a star, and a commit touching more than half the PR's files (at least 3) is skipped as uninformative. `co-change`: files changed together in at least 3 of the last 300 non-merge base commits and in at least half of the commits of the rarer file; commits touching more than 30 files are skipped. Both link each file's first changed symbol.
39. **NestJS plugin choices (M6, PLG-2).** Layers: `@Controller`, `@Resolver`, `@WebSocketGateway`, `@Catch` and `@Injectable` classes implementing `CanActivate`, `NestInterceptor`, `PipeTransform`, `NestMiddleware` or `ExceptionFilter` → api; other `@Injectable` and `@Processor` → service; `@Entity`, `@Schema`, GraphQL object/input/args types and classes with only validation decorators (DTOs) → data; classes implementing `MigrationInterface` → schema; `@Module` → config. Test files keep their path layer; config globs still win. Edges: injection only when the constructor parameter is new in the PR (existing injections are already covered by `calls`), producers (`queue.add('job')`, `emit('evt')`, `send('pattern')`, `@InjectQueue('q')`) to changed handlers (`@Process`, `@Processor`, `@OnEvent`, `@EventPattern`, `@MessagePattern`), migrations to the entity columns they name. This answers the 2026-10-31 question about `to-failed.action.ts`: an `@Injectable()` class is a service wherever its folder is.
40. **Review hints in the report (M6, HINT-1, UI-4).** Every hint names a group, step and hunk. The report shows them where M4 already did: as chips on the group card (all hints of the group). Showing them on the step or file they point at would be a UI change; it goes through the design canvas first. SQL files stay text-only (tier 0) and in the `schema` layer. Markdown uses `tree-sitter-markdown` v0.5.3 from its GitHub release (not on npm with a `.wasm`), YAML `@tree-sitter-grammars/tree-sitter-yaml` 0.7.1. Underlined (setext) headings do not open sections in this grammar.

Reasons give each pair of symbols at most one sentence, so a framework edge and a shared literal about the same entity column do not take two of the six places.

45. **Benchmark design (M7, §12.3).** Cases: runs of 3–6 consecutive commits on the first-parent line of the default branch, each with one parent, 1–20 files and a code file outside docs and tests, and not a release, dependency bump, revert or CI change; sizes cycle 3, 4, 5, 6; at most 10 per repository, most recent first, saved with their SHAs in `bench/cases/*.json`, which is git-ignored: the owner does not publish which repositories are used and names them to `bun run bench:select <owner/repo> …` on each machine; every run on that machine scores the same commits. Each case is squashed into one synthetic PR (base → last commit) whose single commit hides the real boundaries, so `same-commit` cannot leak the answer; `co-change` still reads the 300 commits before the base, as for a real PR. Ground truth: an added line belongs to the commit `git blame` names, a deleted line to the commit after the last one `git blame --reverse` finds it in; a hunk to the commit owning most of its changed lines ("mixed" hunks counted in the report). Score: ARI over labeled hunks, also over code hunks only (without generated and formatting-only hunks, which Bowi collects in one noise group by design). Baselines: one group (alphabetical), top folder, and the file's own folder, added because many repositories keep all code under `src/` or `packages/`, where top folder equals one group. Verdict: supported when Bowi's mean ARI is at least 0.10 above the better folder baseline and at least as good in two thirds of the cases. Plugins are on; outside references are off (they do not change groups). Repositories need clean history: one candidate was dropped because dependency bots and 25–101-file commits left no run of 3 clean commits. The benchmark downloads from GitHub (commits and trees, then the file versions each case needs); it is a development tool, not part of Bowi's runtime privacy rules (NFR-3).
46. **Moves pair exactly two hunks (M7 fix).** The benchmark found a real PR that failed with exit code 3: a type moved a few lines within one hunk was paired with its own hunk, and the "Moved without changes" step listed the hunk twice (partition violation). The same happened when one hunk's code moved into two different hunks. Moves are now kept only when they pair two distinct hunks one-to-one (§15 #13 still applies inside such a pair); anything else stays an ordinary change. The check repeats until stable, because dropping a pair can leave another hunk only partly covered by moves.
47. **Reordered lines are not formatting (M7 fix, refines NOISE-2).** A hunk was formatting-only when its changed lines had the same fingerprint on both sides, so lines that kept their text but changed places (swapped `app.use()` middleware, reordered statements) were collapsed as noise although order can change behavior. The fingerprint now covers the whole hunk, context lines included: reformatting still matches, a reorder does not. Found while writing the tests for #46; the email-verification fixture's `date.ts` is still formatting-only.
48. **What the weakest benchmark cases showed (M7, `bun run bench explain <case>`).** Four cases scoring 0.00–0.21 were studied. Case 1: three small fixes in one folder whose code calls each other; Bowi follows the code, the split is only the authors' choice; nothing to fix. Case 2: two general bugs, fixed: (a) the last line of a multi-line import (`} from "../utils/test-utils"`) was not recognized as an import, so its path counted as a shared literal and joined unrelated tests; (b) symbols in test folders (test entities, fixtures, helpers) could never be the target of a link, so a new test was separated from the entity it imports; now test code links to the test symbols it uses (calls / uses-type), and application code is still never linked to test code. Case 3: several commits change one package through shared helpers (real links), and many fixture files are tied to their module only by folder name (`fixtures/<module>/`), a convention-specific rule left for later. Case 4: one commit only adds tests for code another commit changes (Bowi rightly links them), and a DTO, an OpenAPI JSON file and a generated SDK are linked only by type names across languages; not cheap to fix. Result of (a) and (b): overall 0.51 → 0.52, the weakest repository 0.41 → 0.44, 5 cases better, none worse.
49. **How AI enrichment runs (M8, AI-3, AI-4).** One call per logic group (moved code and noise are never sent), up to 3 at once, 2 minutes each, then one call for the PR overview made from the groups' new titles and intents. The stage runs right after groups and before outside references and hints, so hints already point at the final groups. Sent per group: PR title, description (first 3,000 characters) and commit subjects (AI-4 lists title and description; subjects are the same kind of metadata and help local runs, which have neither); rule-based title, reasons, steps, changed symbols; the diff with 2 context lines around each change, at most 80 lines per hunk and 600 per group (further hunks by header only); the other logic groups' ids, titles, files and symbols, so a move has somewhere to go. A failed, late or invalid answer keeps the rule-based text for that group; warnings are written in group order so they do not depend on which call finished first. Errors every further call would hit (not installed, not logged in, unknown flag, usage limit) stop the remaining calls with one warning; the run still exits 0, since AI is optional and the report is complete without it. `claude` missing entirely is checked before the analysis and exits 1 (CLI-12).
50. **`claude -p` hardening (M8, verified on Claude Code 2.1.314).** `-p --output-format json`, `--tools ""` (no tools: a single answer), `--strict-mcp-config` (no MCP servers), `--disable-slash-commands`, `--no-session-persistence`, `--system-prompt` (Bowi's own, replacing Claude Code's), `--json-schema` (the answer schema, generated from the zod schemas that validate it again), `--model` when configured, the prompt on stdin, an empty temporary working folder. `--safe-mode` keeps the user's CLAUDE.md, hooks, plugins, skills and MCP servers out while the login still works; `--bare` would do the same but reads only `ANTHROPIC_API_KEY`, never the Claude Code login, so it does not fit the decision in #6. Checked: without `--safe-mode` the session quoted the user's global CLAUDE.md, with it, it did not. The child gets the user's environment without `GITHUB_TOKEN` / `GH_TOKEN`. The prompt marks repository text as data and tells the model to ignore instructions in it; whatever comes back is only ever shown as escaped text.

For pull requests the repository's `ai` section is ignored with a warning; `--ai`, or `--config` with the reviewer's own file, turns it on. `--local` honors the working tree's `.bowi.json` (the reviewer's checkout).

55. **Determinism with AI on (M8, NFR-2, AI-6).** Answers depend on the model, so GRP-12 holds only with AI off (as NFR-2 says). Answers are cached under `<cache>/ai/` by a SHA-256 of the prompt version, provider, model setting, system prompt, prompt and schema; only valid answers are kept. A second run on the same changes therefore asks nothing and produces the same plan. Changing a prompt means bumping `PROMPT_VERSION` in `@bowi/ai`.
56. **Reading order: dependencies go right before what needs them (M8 fix, refines #33).** Steps (and groups, and files in a step) were ordered by repeatedly taking the earliest item, in layer (or size) order, whose dependencies were all placed. In a NestJS pull request the Data shape step used an interface in "Other code" (`interfaces/` has no layer rule), so it had to wait, and the UI step, which uses nothing, became the earliest ready one and was read first: UI → interface → Data shape → Services → Tests. Now items are taken in layer (or size) order and the dependencies not placed yet go right before the item that needs them: interface → Data shape → Services → UI → Tests. For groups this also stops an independent group from overtaking a larger one that waits for a small dependency. The benchmark is unchanged (it scores the partition, not the order): 0.52, 28 of 37.
57. **Imports and injected constructor parameters go with the code using them (M8 fix, GRP-3).** An added import, or a constructor parameter that injects a dependency (`private readonly eventEmitter: EventEmitter2,`), is in its own hunk, apart from the methods that use it. Such "glue" has no useful links of its own (the import names a module; the parameter an external type), so clustering placed it by whatever link it had: in a NestJS pull request two services' imports formed a group of their own through a co-change link, another import went to the UI group through co-change with an HTML file, and the constructors of three services followed an unchanged parameter's type into a second "emit events" group. Now a unit whose hunks are only TypeScript/JavaScript imports or constructor parameter properties is glue when code in the same file uses a name it introduces (string literals ignored, so `from 'node:events'` does not use a field `events`); after clustering, it moves to the group of the code using it most, following glue used by glue (import → constructor parameter → methods using the field). Moving it last keeps group formation unchanged: a first version merged glue into its user before clustering, which changed what Louvain split (one case 0.76 → 0.55); another left glue out of clustering, which lost real links that run through import lines (one case −0.04). Benchmark: 4 cases better (+0.01 to +0.02), 1 case −0.01, mean 0.52 (the weakest repository 0.44 → 0.45). In that pull request the imports-only group and the second "emit events" group are gone: each service's import, constructor and emitting methods are read together.
58. **`interfaces/` and `types/` are Data shape (M8, SYM-4; owner's decision 2026-10-31).** `interfaces/`, `types/` folders and `*.interface.ts`, `*.types.ts`, `types.ts` files are in the `data` layer, read with entities and DTOs. Before, e.g. `src/orders/interfaces/order-event.interface.ts` was "Other code" (#56).

Running from the sources still needs Node 22.18, which strips TypeScript types by default.
60. **One published package (M9; owner's decision 2026-11-01).** Only `@bowi/cli` is published (npm refused the name `bowi` as too similar to existing packages, §15 #1; scoped names are not checked for that); it installs the `bowi` binary. `scripts/build-package.ts` bundles every `@bowi/*` package with esbuild into `dist/bowi.js`; `dist/bin.js` checks Node and loads it with a dynamic import. Third-party packages stay dependencies, pinned exactly; the build fails if the code imports a package no internal package declares, or one with a version range. Grammars, queries and the page template are copied next to `dist/`: the code finds them, and `package.json` for the version, one folder up from its own module, which holds in `packages/<name>/src/` and in `dist/` alike, so no path helper was needed. `os` was `darwin` and `linux` until Windows was supported in 0.1.1 (npm refuses to install instead of installing something that fails); it is `darwin`, `linux` and `win32` since (§15 #63). Publishing the internal packages would make everything they export public API; other tools have `review-plan.json` (U3). The `@bowi` scope is the owner's npm org `bowi`, so no one else can publish `@bowi/*` names that look official.
61. **git ≥ 2.31 (M9, NFR-6).** The oldest git that has everything Bowi uses: `GIT_CONFIG_COUNT` (2.31), which passes a GitHub token to git without putting it on the command line; `fetch --no-write-fetch-head` (2.29); `--pathspec-from-file` (2.25); `--end-of-options` (2.24); partial clones with `--filter=blob:none`. `checkGit()` runs `git --version` before every analysis (a few milliseconds) and exits 2 with how to install git when it is missing or older.
62. **Releases from a private repository (M9; owner's decision 2026-11-01).** The repository stays private for now; the `@bowi/cli` package is public. 0.1.0 is published by hand (npm's trusted publisher is configured on an existing package). From then on, `.github/workflows/release.yml` runs on a `v*` tag and only *stages* the version (`npm stage publish`) through npm trusted publishing (OIDC, no npm token in GitHub); it goes out when the owner approves it with 2FA, and a version already on npm is skipped. Because the repository is private: GitHub Free has no environments for private repositories, so the workflow and the npm trusted publisher name none, and staged publishing is what keeps a changed workflow from releasing on its own; npm makes no provenance; CI runs on Linux, and on Windows with one Node version per job since 0.1.1 (Windows minutes count 2×), not on macOS (minutes count 10×; macOS is checked on the owner's machine); the npm page's repository and issue links, and the README's links to `docs/`, are dead until the repository is public. The package code is readable anyway (`dist/bowi.js` is not minified, MIT). npm's trusted publisher must publish once within 2 days of being added ("Pending validation"); the one added on 2026-11-01 was left to lapse rather than release a 0.1.1 without changes, so it is added again shortly before the next release. Going public: add `environment: npm` to the workflow and to the trusted publisher, add macOS back to CI; later versions then get provenance.
63. **Windows in 0.1.1 (M9.1; owner's decision 2026-11-02).** Windows ships on its own as a patch release instead of with line comments in 0.2.0 (#3, plan M10), because the owner works on Windows; it adds no features. What Windows needed: (a) **line endings**: with `core.autocrlf=true` (Git for Windows' default) or `text`/`eol` attributes, files on disk have CRLF while `git diff` shows LF, so the head text read from disk differed from the diff in every line. The local source now asks git which files it converts (`git ls-files --eol` on the temporary index, plus `core.autocrlf`) and reads those with CRLF turned into LF, following git's rules: always with `text` or `eol`; with `text=auto`, or no attribute and autocrlf true/input, only when the index copy has no CRLF. `git grep` lines drop a trailing `\r`. (b) **hooks**: Git for Windows reads `core.hooksPath=/dev/null` as `<drive>:\dev\null\`, a folder any local user may create, so on Windows Bowi passes `NUL` (a reserved name that can never be a folder); `-O/dev/null` works because Git for Windows opens `/dev/null` as `nul` (both checked with Git for Windows 2.50.1 through Node's `spawn`). (c) the cache is `%LOCALAPPDATA%\bowi`. (d) the report is opened with `explorer <path>`, not `cmd /c start` as the plan said: cmd.exe would read `&` or `^` in an `--out` path as commands. (e) `--ai` runs only the native `claude.exe`: npm's `claude.cmd` needs cmd.exe, which cannot pass the multi-line `--system-prompt` (and putting the prompt in a file would change the hardened call); when only a `.cmd` is on PATH the error says to install the native Claude Code. (f) Windows keeps a just-stopped process's working folder locked for a moment, and refuses to rename over a file another process has open: both are retried or ignored where the result is the same. Symlinks need nothing: Git for Windows checks them out as small files holding the target path (`core.symlinks=false`, its default), which is what git diffs. CI adds `windows-latest` for `bun run check` (Node 24) and the smoke test (Node 22.12.0).
64. **Comments survive re-runs (M10, CLI-15).** A run writing into a folder whose `review-plan.json` holds a review of the same repository and pull request (or branch) carries it over before overwriting the file. A comment moves to the first place, nearest to where it was, where its snippet's lines read the same (same kinds, same text) in a hunk of the same file, or of the file it was renamed to; otherwise it becomes `outdated` and keeps its anchor, snippet and the head it was written on, as GitHub does after a push. File comments stay while the file is in the diff. Outdated comments never come back. Nothing is dropped: comments that are invalid or belong to another review leave the old plan in `review-plan.json.bak` with a warning. Anchors move with the comment's `headSha`; `hunkId` follows the new hunk.
65. **How comments are saved (M10, CLI-13; owner's decisions 2026-11-01 and 2026-11-05).** A page opened as a file cannot write to disk. `bowi serve <dir>` (or `--serve` on a run) serves the folder's `review.html` on `127.0.0.1`, on a free port, with an 18-byte random token: in the address (`?t=`) for the page, in an `X-Bowi-Token` header for `GET` / `PUT /api/review`. The `Host` header must be the server's address (DNS rebinding) and an `Origin`, when sent, the page's own; saves must be JSON, at most 32 MB, valid against the review schema, and name the `generatedAt` of the plan they were made on (409 after a re-run, so the page reloads instead of writing stale anchors). The page is sent with a Content-Security-Policy that allows only its own inline code and requests to the server, and `Referrer-Policy: no-referrer` (the token is in the address). A save writes the plan and the review inside `review.html` atomically, one save at a time. The page saves every change at once (typing in the summary after 0.6 s), shows the state next to the tabs, and keeps a failed save as a draft. Runs still write a static file and exit; serving by default is to be reconsidered after using it.
66. **Comment text is Markdown rendered in the page (M10, UI-15, UI-26; owner's request on the canvas).** Comments are written in the page, so they cannot be rendered at report time like the description. micromark with GitHub-flavored Markdown runs in the page with raw HTML off: tags in a comment show as text and unsafe link schemes lose their address; images become links ("Image: alt"), so the page still loads nothing (UI-1); links to http(s) open in a new tab without referrer; a single line break is a break, as in GitHub comments. This adds about 124 KB to the page template. The page's other markup stays as before: only `DiffLine.html` and `source.descriptionHtml`.
67. **Drafts in the browser (M10, UI-25, UI-27).** Opened as a file, the page starts from the comments embedded when the report was written; new, edited and deleted comments and summary changes are drafts in `localStorage`, per repository and pull request (or branch), so they outlive re-runs; drafts not touched for 30 days are deleted (longer than review progress, UI-12, because they are written work). They show "Not saved". The served page finds them and offers "Save all" or "Discard" (after an inline confirmation); saving applies the changed and deleted comments onto the saved review. A save that fails while serving keeps the change as a draft the same way.
68. **Hiding comments is a view, not data (M10, UI-25; owner's decision 2026-11-05).** "Hide comments" (all) and Hide on a comment (one) last until the page closes; neither is remembered nor written to the plan. Writing a comment shows the comments again. Both tabs share the state.
69. **Comment layout decisions (M10; owner's approval of the canvas 2026-11-05).** A fifth tab, Comments, rather than a side panel; one comment per line range and no replies, since a report has one reviewer; "Clear all comments" clears the summary too; the save status sits next to the tabs; a file can have any number of file comments; in the Changes tab comments look as on a GitHub pull request.
70. **Sending comments to GitHub (M11, CLI-16, UI-28; owner's decisions 2026-11-07).** One direction: the flow is a pull request, a Bowi run, comments in Bowi, then sending them; everything after that is GitHub's job. Bowi reads no comments or review states back, so a chip does not change after the review is submitted, and a comment discarded on GitHub stays read-only here with a dead View link. A sent comment or summary is read-only in Bowi, pending or not, and Bowi never changes or removes anything on GitHub; the server enforces this on every save, so an old tab cannot undo it, and only the server can mark something as sent. The token stays in the local server, which looks for the login each time (`GITHUB_TOKEN`, else `gh auth token`), so `gh auth login` needs no restart. `gh` stays optional and nothing checks for it at install: with no token, the message says whether `gh` is missing or only not logged in. All writes use GraphQL, one comment per request (`addPullRequestReview`, `addPullRequestReviewThread`, `updatePullRequestReview`, `submitPullRequestReview`), not REST as first planned: REST takes all comments at once (one bad line refuses them all), has no file comments in a review and cannot add to an existing pending review. Each comment is recorded as soon as GitHub has it, so a send that stops half way never posts anything twice; after a timeout the page says to look first, since the last comment may have arrived. A line GitHub refuses goes on its file, starting with its lines. An outdated comment, if ticked, goes on its file quoting the old lines. `--yes` stops on new commits, so a script never posts on an old head by accident. Lines are read against a review's commit, so a pending review on another commit than the report's stops the send, and a pending review rules out "Post now". The API shapes were checked against GitHub's live schema; posting itself is tested against `fake-github.ts`.
71. **Pending and posted must not look alike (M11, UI-28; owner's feedback on the canvas 2026-11-07).** Both first read "On GitHub", and a dismissible banner was the only way to the submit button. Now each has its own chip, words and color everywhere. Because Bowi reads nothing back, the reminder words itself to stay true after the submit ("If you already did, there is nothing more to do"). Changed 2026-11-09 (owner's request): "Open on GitHub", always at the top of a pull request's report, replaces "Submit on GitHub" there, so the reminder can be dismissed again without losing the way to GitHub.
72. **Marking a pending review as submitted (M11, UI-28; owner's request 2026-11-09).** Bowi reads nothing back, so after the reviewer submits on GitHub the chips would keep saying "Sent as pending". "I submitted it" lets the reviewer say so: every pending comment and the summary become "Posted" in one click, with Undo in the message that follows (an inline confirmation in the reminder broke its layout, owner's feedback the same day). All at once, because GitHub submits a pending review as a whole. Only the server makes this change, through its own request (`POST /api/review/posted`, `setPosted`): a save still cannot change anything that was sent, so an old tab cannot undo it. Only in the served page, which can save it. A re-run keeps the record as it is, so comments sent as pending stay so until marked.
73. **A token pasted in the post dialog (M11, UI-28; owner's decision 2026-11-09).** Of four ways to give the dialog a login (paste a token; paste and remember it in the system keychain; "Sign in with GitHub" through the device flow, which needs a GitHub or OAuth App registered for Bowi; start `gh auth login` from the page), only pasting, kept in memory. "Use another token" works also when `gh` or `GITHUB_TOKEN` gives a login, and takes an optional name, shown as "token “Work”". The page sends it once to `bowi serve` (`POST /api/github/token`), which checks it with GitHub, keeps it only if GitHub accepts it, and uses it before the logins it finds until it stops or "Use my usual login" (`DELETE`). It is never written to the plan or the page, printed, or sent back to the page, and the page keeps no copy. `bowi comments push` still uses `GITHUB_TOKEN` or `gh`.
74. **Single-file components without new grammars (M14, PARSE-2).** The plan was to vendor tree-sitter grammars for Vue and Svelte. Instead `@bowi/lang` blanks everything outside the scripts (Vue and Svelte `<script>` blocks, Astro's frontmatter and `<script>` tags) and parses the rest with the TypeScript grammar already vendored, so symbols, references and lines are exact, there is no ABI risk against web-tree-sitter and no extra `.wasm` in the package. The markup stays text but is not ignored: component tags (`<UserCard>`, `<user-card>` → `UserCard`) and names in bindings and expressions (`@click="save"`, `{count}`, `{{ total }}`) become references, and markup counts in content lines and fingerprints with its whitespace collapsed, so a template-only change is a real change while re-wrapped tags are formatting. A JSX script (`<script lang="tsx">`) is parsed as TypeScript and may fall back to text. Import resolution knows `.vue`, `.svelte`, `.astro` and SvelteKit's `$lib`.
75. **Front-end framework plugins (M14, PLG-3; owner's decisions 2026-11-05 and 2026-11-10).** Eleven plugins, tried in order so that a meta-framework names a file's layer before the library it builds on: NestJS, Angular, Next.js, React Router, Nuxt, SvelteKit, Astro, Vue, Svelte, SolidJS, React. JSX uses, hooks and context in React and Solid are ordinary references the graph already follows, so those plugins add layers (and a props hint for React); the edges plugins add are what the graph cannot see: components in markup, Nuxt auto-imports, Angular templates, styles and selectors, and file-system conventions (a Next.js or SvelteKit page with its layout, a SvelteKit page with its load function, Next.js `loading`/`error` files with their page). Route hints are derived from file paths; new pages give an info hint, new or changed API routes too (attention when new). Routes, layouts and edges were checked on the grouping benchmark with public repositories for each framework, chosen with the owner and kept private like the others.
76. **Back-end Node.js frameworks (M14, PLG-3; owner's request 2026-11-12).** Express, Koa, Fastify and Hono share one plugin shape: a file is API when it imports the framework or registers routes on a router-like name (`router.get(…)` on one line), and a changed line that mounts a router or plugin (`use`, `route`, `register`, `mount`) depends on the changed file it imports it from, which the graph cannot see when the import is a default export under another name. Route hints stay the generic `public-route` rule. tRPC routers and setup are API, and a client call on a changed line (`.user.byId.useQuery()`) depends on the changed router whose changed line defines `byId`; new procedures get a hint. Database libraries set layers only (TypeORM also links migrations to entity columns, as for NestJS) and come before the HTTP frameworks in plugin order, so a model stays data. AdonisJS, Elysia and Hapi were left out: path rules already read Adonis's `controllers/` and `models/`, and the others had no public app with a usable history for the benchmark.
77. **Reading order, from the owner's feedback on three pull requests (M14, GRP-7, GRP-8; 2026-11-16).** (1) Groups that do not depend on each other are read foundations first, by the earliest layer of their code (tests and docs count only in a group of nothing else), then larger first: a group of services before a group of UI. (2) Steps that use each other only because a layer step holds files on both sides of another step (a router used by a new module that `server.js` then calls; both the router and `server.js` are API) are split along their files' dependency order, so each file comes after what it uses; the extra step's ID gets a suffix (`g1:api-2`). Steps whose files really use each other keep the layer order. (3) Tried and dropped: making a monorepo's workspace package imported by its name (`@acme/permissions`) visible to the importer, found by folder. It helped three benchmark repositories but lowered the mean on nine (0.434 → 0.425, still 0.429 when only exported symbols counted), so it is not in. (4) Names in a re-export (`export { a } from './x'`) are uses, so a changed barrel file depends on what it re-exports; `export { a as b }` uses `a`. With §15 #11's workaround, a barrel using `export type *` is parsed at all.
